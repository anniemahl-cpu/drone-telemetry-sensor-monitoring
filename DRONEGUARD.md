# DroneGuard

**A physics-informed digital twin and anomaly-detection extension of the ESP32 drone telemetry prototype.**

The original hardware project integrated an ESP32, MPU6050 IMU and INA240 analogue sensor output into a timestamped CSV stream. DroneGuard begins where that prototype ends: it audits telemetry, estimates broad motion states, creates controlled simulated flight scenarios, compares anomaly-detection strategies, and presents the results in an interactive dashboard.

## Research question

> Can a physics-informed software system distinguish normal motion from potentially unsafe telemetry patterns when only limited real-world sensor data are available?

## Scientific scope

DroneGuard maintains explicit provenance:

- **REAL BENCH DATA** means the original ESP32 recording. It is not described as real flight data.
- **SIMULATED FLIGHT DATA** is generated by the software digital twin.
- **MODEL INFERENCE** is an experimental result, not a certified safety diagnosis.
- The original INA240 value is an **uncalibrated analogue output** and is never presented as current in amperes.

The original recording is approximately 2 Hz and contains about one minute of stationary/manual-motion/stationary data. That is useful for baseline noise and transition analysis, but it is not sufficient to validate a multi-class real-flight fault classifier. Simulation is therefore used to create controlled, reproducible experiments—not to manufacture claims of real-world validation.

## Features

- CSV schema and formula consistency checks
- Sampling-rate, missing-data and timestamp diagnostics
- Motion score, jerk and angular-rate features
- Nine deterministic digital-twin scenarios
- Simplified battery state-of-charge and voltage-sag model
- Sensor noise, bias, freezing and packet-loss injection
- Engineering rules + Isolation Forest + Random Forest hybrid detector
- Risk timeline and downloadable health report
- Reproducible sampling-rate experiment
- Automated tests and GitHub Actions

## Scenarios

`normal`, `gust`, `aggressive_manoeuvre`, `thrust_loss`, `battery_sag`, `current_spike`, `imu_bias`, `sensor_freeze`, and `packet_loss`.

These are simplified computational scenarios. Their labels describe the injected model condition, not a certified mapping from the original sensor recording to real drone faults.

## Evaluation policy

Data from independent random seeds and complete simulated missions are used for evaluation. Adjacent samples from the same mission are not randomly split between training and testing, because that would inflate apparent performance through temporal leakage. The project reports macro F1 and is designed to add false-alarm rate and detection-delay experiments as the next milestone.

## Limitations

- The dynamics model is deliberately simplified and is not a flight-control simulator.
- The original 2 Hz recording cannot represent motor/propeller vibration or validate flight control.
- Synthetic faults do not prove real-flight fault-detection performance.
- An accelerometer/gyroscope alone cannot uniquely diagnose every mechanical or electrical fault.
- INA240 conversion to amperes requires hardware calibration and shunt/gain information.
- This project must not be used to make real flight-safety decisions.

## Suggested next experiments

1. Measure macro F1 from 100 Hz down to 2 Hz.
2. Sweep sensor noise and timestamp jitter.
3. Hold out one fault class to test unknown-anomaly handling.
4. Estimate simulator noise parameters from the original stationary baseline.
5. Compare rules, Isolation Forest and the hybrid detector using mission-level splits.

## Relationship to the original project

This extension preserves the original engineering narrative: a physical telemetry prototype revealed limitations in sampling, calibration and labelled-data availability; DroneGuard turns those limitations into explicit computational research questions.
